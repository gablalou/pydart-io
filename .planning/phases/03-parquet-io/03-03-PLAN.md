<objective>
Add read-side predicate pushdown and column projection (PARQ-04, PARQ-05) to `from_parquet`.
After this plan a user can do something they could not before: read only the columns they want
(`columns=[...]`) and only the rows matching a set of AND-combined comparison filters
(`filters=[(col, op, value), ...]`), with the returned Table containing ONLY matching rows.

D-26 defines pushdown as BOTH halves: row-group-level skipping driven by the statistics Plan 02's
writer emits, AND exact row-level filtering within surviving groups. Critically, PARQ-04 is the
*write-stats-enable-skip* guarantee — so this plan verifies the skip decision itself in isolation
(a flint-core unit test on `surviving_row_groups`), not just that the final rows are correct (which
row-level filtering alone would satisfy even if pruning never engaged).

The filter comparison logic is the highest-correctness-risk surface (RESEARCH A3), especially the
`!=` operator's asymmetric skip rule. All filter logic is built ONCE per call and consumed by both
the skip decision and the row filter — never re-derived (single-source-of-truth, pandas_plan.rs precedent).

Purpose: complete PARQ-04 (statistics-driven pushdown) and PARQ-05 (projection + predicate) honestly.
Output: `parquet_filter.rs` (FilterExpr/Op + could_match_range, exhaustively unit-tested),
pushdown/projection wiring in the read path, a Rust row-group-pruning test, and Python pushdown tests.
</objective>

| Parquet row-group statistics -> surviving_row_groups | Statistics read from the (untrusted) file drive skip decisions; a wrong comparison silently drops matching rows. |

Verified by (a) exhaustive flint-core unit tests and the parquet_row_group_pruning integration probe, and (b) the Python baseline property test comparing filtered reads against an unfiltered-then-filter baseline across all six operators + boundaries — over-pruning (dropping matching rows) is caught, satisfying D-26's no-false-result contract (ASVS V5). |
