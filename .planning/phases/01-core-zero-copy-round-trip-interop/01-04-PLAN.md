<objective>
Complete the ecosystem-interop half of Phase 1: import a foreign Arrow object into a flint `Table` zero-copy via the Arrow PyCapsule Interface (CAP-02), and validate the full export+import round-trip against all three consumers locked by D-05 — pyarrow, Polars, AND DuckDB — not just pyarrow. This is the delegation-heavy half of the phase (RESEARCH.md line 49-51, 196-205): compose `pyo3-arrow`'s existing `FromPyObject` marshalling rather than hand-rolling FFI, while still validating untrusted foreign capsules before trusting them (Security Domain).

Purpose: The zero-copy claim is only credible if real ecosystem libraries accept and produce flint Tables without copies (CONTEXT.md specifics). D-05 explicitly requires DuckDB to be proven in Phase 1, not deferred. This plan handles the untrusted-input security surface (CAP-02 accepts an arbitrary object claiming protocol compliance) and the two documented interop pitfalls: DuckDB's non-idempotent `__arrow_c_stream__` and its unconfirmed native-consumption status.

Output: `from_arrow` import (CAP-02) with capsule validation; `tests/python/test_interop.py` proving CAP-01 export to + CAP-02 import from pyarrow, Polars, DuckDB — starting with an empirical DuckDB spike.

Covers CAP-01 (full 3-library export), CAP-02 (import, D-05). Composes `pyo3_arrow::PyTable` (D-01 Table type). This plan and Plan 03 run in the same wave (no shared files).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| foreign library object → flint `from_arrow` (CAP-02) | An arbitrary caller-supplied object claiming Arrow PyCapsule compliance crosses into Rust and is dereferenced |
| flint `Table` export → external consumers | flint hands a capsule to pyarrow/Polars/DuckDB (their consumption is their responsibility) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Tampering / DoS | `from_arrow` import of an untrusted foreign capsule (`crates/flint-python/src/import.rs`) | high | mitigate | Treat the foreign object as untrusted input (ASVS V5): delegate marshalling to pyo3-arrow's validated `FromPyObject` path (non-null pointers, schema/array-length/offset consistency) and add NO unchecked `unsafe` shortcut around it; surface inconsistency as `flint.FlintError`, never a panic/segfault (RESEARCH.md Security Domain). |
| T-01-09 | Denial of Service | consuming a foreign `__arrow_c_stream__` more than once | medium | mitigate | Consume each foreign capsule/stream exactly once and materialize immediately; DuckDB relations raise `Invalid Input Error` on a second call (RESEARCH.md Pitfall 3). Enforced in both `import.rs` and the interop tests. |
| T-01-10 | Repudiation | DuckDB interop silently skipped due to unconfirmed native consumption | medium | mitigate | Empirical spike at test setup selects native vs pyarrow-intermediary path; DuckDB is proven either way and the path is recorded (D-05, Open Question 1) — never skipped. |
| T-01-SC | Tampering | pyarrow/polars/duckdb consumed as test dependencies | high | transfer | These are dev/test-only consumers, already cleared in the Plan 01 Package Legitimacy Audit (T-01-SC); interop correctness relative to their protocol behavior is the upstream libraries' responsibility. |
</threat_model>
