<objective>
Close the one blocking verification gap for Phase 1 (CR-01 / Truth 1, CONV-01/CONV-02): `import_column_via_pandas_stream` in `crates/flint-python/src/pandas.rs` reads only the FIRST `RecordBatch` off a column's Arrow C stream (`.batches().first()`) and silently discards every subsequent batch. This causes silent, unsignaled data loss for any Arrow-backed column whose underlying data spans more than one chunk — the canonical trigger being an ordinary `pd.concat([df1, df2])` of two `ArrowDtype`-backed frames. Reproduced empirically: a 6-row / 2-chunk `int64[pyarrow]` DataFrame round-trips through `flint.Table.from_pandas(df).to_pandas()` and returns 3 rows, no exception.

Purpose: Convert this silent truncation into a correct, honest conversion. Per 01-REVIEW.md's CR-01 fix, concatenate all batches' column-0 arrays via `arrow::compute::concat` (an honest copy for the multi-chunk case, which was never a single contiguous buffer to begin with) — while preserving the genuinely zero-copy single-chunk path the phase's pointer-identity proof (D-06) already certifies. Add a regression test so this defect class cannot silently recur.

Output: A corrected `import_column_via_pandas_stream`; a multi-chunk `ArrowDtype` round-trip regression test in the Python suite; a green `cargo test --workspace` and `uv run pytest tests/python/ -q`.

Scope: CR-01 only (CONV-01/CONV-02). The other six 01-REVIEW.md findings (WR-01..WR-04, IN-01, IN-02) were NOT flagged as verification gaps and are explicitly out of scope for this plan — do not fold them in.
</objective>

    Fix `import_column_via_pandas_stream` in `crates/flint-python/src/pandas.rs` so it accounts for EVERY `RecordBatch` in a column's Arrow C stream instead of only the first one. Follow 01-REVIEW.md's CR-01 fix, with one deliberate refinement to preserve the zero-copy guarantee:

    1. After importing `PyTable` from the capsule, read `py_table.batches()`.
    2. If `batches` is empty, keep the existing explicit error (`FlintError::Other("column stream produced no record batches")`) — never a silent empty result or a panic.
    3. If `batches.len() == 1`, return `batch.column(0).clone()` exactly as the current code does. This is the genuinely zero-copy single-chunk path (the borrowed Arrow buffer is Arc-shared, not copied) that the D-06 pointer-identity proof depends on. Short-circuiting here keeps that guarantee independent of `concat`'s internal single-array behavior.
    4. If `batches.len() > 1`, collect each batch's column-0 array (`batch.column(0)` as `ArrayRef`) into a `Vec`, then concatenate them with `arrow::compute::concat` over the batches' column-0 arrays (borrow each as `&dyn Array` / `a.as_ref()` to build the `&[&dyn Array]` slice `concat` expects), mapping any error via `FlintError::from`. Return the concatenated `ArrayRef`. This turns the multi-chunk case into an honest single copy — a multi-chunk column was never one contiguous buffer, so this does not regress the single-chunk zero-copy case.

    `arrow::compute::concat` is provided by the `arrow` crate's non-optional `arrow-select` component; no new dependency or Cargo feature is expected. If the build reports it missing, enable the appropriate `arrow` feature rather than hand-rolling a batch-appending loop or reaching for `pyo3-arrow`.

    Do NOT modify `plan_column` (`crates/flint-core/src/pandas_plan.rs`), `crates/flint-python/src/diagnostics.rs`, strict mode, or `copy_report()`. See the known-limitation note below: multi-chunk diagnostics-honesty is deliberately deferred to Phase 2 (CONV-08), not part of this fix.

    Add a regression test to `tests/python/test_round_trip.py` (e.g. `test_from_pandas_multi_chunk_arrow_dtype_column_preserves_all_rows`): build two 3-row `int64[pyarrow]` DataFrames, combine them with `pd.concat([df1, df2], ignore_index=True)` to produce a 6-row column whose underlying pyarrow ChunkedArray has 2 chunks, then round-trip through `flint.Table.from_pandas(df).to_pandas()`. The lead assertion is `len(result) == 6` (the bug is 3-vs-6 — that is the clearest discriminator); then assert the values equal all six source rows. Do NOT add any strict-mode / copy_report assertions to this test — the multi-chunk strict-mode behavior is a Phase 2 concern and must not be encoded as a contract here.

    TDD: write the regression test FIRST and run it against the current (unfixed) code to confirm it is RED (fails with 3 != 6) — proving it is discriminating, in the spirit of the suite's own `test_from_pandas_fails_loudly_if_a_copy_is_introduced`. Then apply the fix and confirm GREEN.

So the correct closure for CR-01 is an honest copy that preserves all rows, with the multi-chunk strict-mode-honesty explicitly deferred.

| pandas column → Arrow C stream → Rust core | `import_column_via_pandas_stream` consumes a column's `__arrow_c_stream__` export (produced by pandas' own machinery), which may yield any number of RecordBatches. This fix changes how many of those batches are honored. |

Not applicable to this phase: this is an in-process backend data-conversion library with no network surface, no auth/session, no user-supplied query strings — web-app threat categories (injection/session/CSRF) do not apply. The applicable risks are memory-safety and malformed-input handling at the pandas/Arrow FFI boundary.
